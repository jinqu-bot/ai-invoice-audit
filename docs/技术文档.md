# AI 报销审核台 · 技术文档

## 一、项目概述

### 1.1 项目定位

AI 报销审核台面向票据审核中“读得出字段，但解释不清结论”的问题，将图片字段抽取、确定性规则、制度依据、实时处理与人工复核连接成一个可追溯流程。用户选择票据后，可逐张查看识别字段、命中检查、可引用的条款以及处理轨迹；有误时通过复核修正当前结论，同时保留原机器判断。

作品属于基于样例制度的比赛原型，不承担税务验真、付款或最终审批职能。模型只负责观察与结构化提取，业务结论由规则产生；字段质量不足、图片不是发票或处理失败时明确展示边界。展示界面区分真实模型调用、缓存、模拟识别与固定演示数据。

团队：序峰；学校：云南大学。A 戴海青负责后端、AI、规则、部署与主讲；B 易子程负责前端、交互、上传、实时进度、移动端与联调；C 卢豪负责数据集、GT、实拍、评测与文档素材。

## 二、需求分析

### 2.1 角色与使用场景

报销申请人希望批量上传并快速知道需要补什么材料；审核人需要核对图片、字段与制度，避免只得到一个不透明的红绿灯；项目维护者需要分辨识别故障、规则命中和模拟数据，能够复现问题。比赛评审需要在短时间内看到完整链路，并核实结论和指标来源。

高频操作应从上传页直接开始，介绍动画承担讲解任务。首页与上传页已拆分，旧 /#upload 转向 /upload。操作页的入场动画可以跳过，不能成为选择文件与提交的强制前置步骤。

### 2.2 功能需求与验收条件

| 需求 | 实现及验收要点 |
| --- | --- |
| 上传前可核对 | 格式、数量、大小预检；显示文件名、缩略图、大小、总数，支持删除后再提交 |
| 批量任务可观察 | 上传返回 202；逐张进度；成功、部分失败、全部失败文案不同 |
| 判断有证据 | 字段、缺失标记、规则、依据与轨迹一致；技术检查不伪造制度条号 |
| 错误可恢复 | 提交锁定防重复；请求失败保留选择；失败清单按文件名显示 |
| 人工可纠偏 | 确认核对原图、填写理由；保存前后结论和操作者，汇总同步更新 |
| 问答不越界 | 依据检索条款回答，校验条号；无依据时拒答或回退原文 |
| 来源可区分 | provider 与 cached 同时参与展示，模拟、固定演示不能冒充真识别 |
| 结果可复现 | 固定数据集、GT、日期和台账；分开报告规则、字段和端到端指标 |

### 2.3 非功能需求

可靠性通过逐文件异常隔离、落库、任务终态与重启恢复实现。可维护性通过接口集中调用、共享契约、模块化规则和锁定依赖实现。可用性关注桌面与手机导航、图片可读性、动画跳过和失败重试；并不以动画复杂度替代操作效率。

数据边界要求密钥只进入服务端私有配置，运行数据库、上传原图和缓存不进入提交源码。当前原型未实现企业级身份认证、细粒度权限、多租户隔离和高可用集群，不能把界面中的复核人文本等同于经过认证的身份。

## 三、系统架构设计

### 3.1 分层与数据流

| 层 | 组成 | 输入与输出 |
| --- | --- | --- |
| 浏览器 | Next.js、React、TypeScript、Tailwind、GSAP、Lenis | 文件选择与操作；展示字段、进度、证据及复核结果 |
| API | FastAPI、Pydantic、路由与统一错误结构 | 校验上传与请求；返回批次、详情、问答和汇总 |
| 任务与 AI | runner/jobs、图像准备、视觉 provider、校验重试 | 图片到字段；逐张生成结构化结果与任务事件 |
| 业务判断 | R0-R8、台账、制度条款、复核服务 | 字段和上下文到规则命中、结论及变更记录 |
| 持久化与代理 | SQLite、文件、nginx、systemd | 保存状态与原始证据；代理 HTTP/SSE、管理进程 |

主数据流：浏览器预检并提交 → API 创建批次并返回 202 → 后台逐张准备图片与抽取字段 → 校验与规则审核 → 落库并发布 SSE → 浏览器更新卡片、详情和计数。模型异常影响当前文件，批次汇总保留成功项及失败原因。

制度问答使用独立检索和文本模型路径；可选 Function Calling 也为旁路。两者不绕过规则直接修改审核结论。人工复核通过专用接口形成持久化事件，当前展示状态读取最新有效复核结果。

### 3.2 契约、状态与异常

后端 `backend/app/schemas.py` 定义结构，前端 `frontend/src/lib/types.ts` 对齐；请求集中在 `frontend/src/lib/api.ts`。真实上传接受后返回 202 与 processing；固定演示可直接返回 200 与 done，不能强行要求所有成功请求均为同一状态码。

批次终态 done、partial、failed 描述文件处理是否成功；单张 verdict 的 pass、suspect、reject、manual 描述业务结论，二者不能混用。“驳回”是有效审核结果，不等于文件处理失败。全部文件失败时应显示全部失败，不显示“其余照常审完”。

SSE 推送逐张完成与批次结束事件；前端在需要时重新拉取结果，避免只依赖瞬时事件。缓存与来源标记通过同一接口字段到达卡片和详情，避免序列化白名单漏字段后两处展示冲突。

### 3.3 存储设计与可追溯性

SQLite 保存批次、发票、台账及复核等数据；上传文件和抽取缓存位于本地目录。演示、模拟和真实来源在展示与台账逻辑中区分，避免模拟号码被解释为用户真实报销记录。批次任务落库后才暴露查询标识，减少上传返回后立即查结果出现 404 的竞态。

复核记录保存旧结论、新结论、理由、操作者与时间；原始机器判断仍可追溯。四类数量按最终展示结论汇总，改判不改动金额或失败文件清单。当前使用单机 SQLite，适合比赛规模，生产扩展需要数据库迁移、权限与任务队列设计。

## 四、AI 技术方案

### 4.1 选型理由与集成边界

视觉语言模型可以从票面图片提取名称、号码、日期和金额等异构信息，避免为每一种版式单独写坐标模板。结构化输出后交给规则引擎，能够把“读图错误”与“制度判断错误”分开定位。文本模型负责制度问答和可选工具编排，不代替确定性审核。

采用 OpenAI 兼容 HTTP 协议，由 httpx 调用模型服务，主要配置为 API key、base URL、model；更换服务仍需确认其支持图片输入、输出格式和推理参数，不能保证任何同名协议服务都无条件兼容。冻结评测记录的模型标识是 deepseek-flash，provider 为 openai-compat；这里引用的是项目记录中的服务标识，不推断其上游权重或训练来源。

无视觉 key 或基础地址时回退 mock-vlm，它按样例返回数据而非读取票面；固定演示批次为 fixture。可运行降级便于无额度联调，但所有成绩必须使用对应真实识别导出，不能从 provider 名称或演示成功推断准确率。

### 4.2 图片准备与结构化抽取

前端可选压缩对大于等于 1 MB 的文件处理，长边最多 2560 像素、JPEG 质量 0.92；压缩变大或解码失败则使用原图。后端再按 IMAGE_MAX_EDGE（默认 1024）处理送模图片。两级压缩降低传输体积，同时可能损失小字，评测时必须记录压缩开关，不能假定所有图片缩小后仍同样清晰。

提示词要求字段来自图片、看不清返回 null、不要依据常识补全或反推金额，并提供字段置信度。解析层处理 JSON、类型、必填字段、日期税号常识与金额关系；金额三件套按小额容差检查。可修正的校验错误回灌模型重试，默认最多 1 次；持续异常保留错误，无法产生有效结果的文件进入失败清单。

输出字段包括票号、日期、购销双方名称和税号、不含税金额、税额、含税金额、税率、类别、明细及缺失信息。缺失金额使用 missing_fields 与空值表达，不能伪装成金额 0，也不能由缺失输入制造明细勾稽违规。

### 4.3 置信度、缓存与复核优化

整体置信度取票号、日期、含税金额、销售方名称、购买方税号五个关键字段的最小值。关键字段缺失会降低其置信度；号码格式异常、非发票和校验错误也限制可用置信度。模型给出的高分只是自报把握，不是正确性的统计保证，已知抬头错字样本证明二者可能冲突。

缓存基于图片指纹，并检查 provider 与模型标识后复用抽取结果；命中时按当前阈值重新判断抽取可用性。规则还依赖当前日期与台账，因此“同图命中识别缓存”不意味着最终业务结论永远不变。界面分别展示本次模型调用和识别缓存命中，计时也随记录说明。

已实现可选抬头裁剪放大核验，但对“公可”被自动补成“公司”的问题仅部分有效，默认 VLM_VERIFY_HEADER=false。它属于有限补救而非彻底解决；更稳健的后续方向是对易混字提供局部原图核对和人工确认。

### 4.4 确定性规则与优先级

| 规则 | 检查内容 | 处理及依据 |
| --- | --- | --- |
| R0 | 抽取置信度不足 | 转人工；技术质量检查 |
| R1 | 已报销票号重复 | 驳回并短路；依赖当前台账 |
| R2 | 关键字段缺失 | 转人工；缺项清单 |
| R3 | 购买方抬头/税号不符 | 驳回；内置制度第 8 条 |
| R4 | 超报销时限 | 存疑；第 15 条，受基准日期影响 |
| R5 | 住宿/招待/办公超标准 | 存疑；按类目引用第 12、5 或 4 条 |
| R6 | 明细金额勾稽异常 | 存疑；技术一致性检查 |
| R7 | 类目与税率异常 | 存疑；规则配置检查 |
| R8 | 敏感类别/关键词 | 存疑；第 9 条 |

结论优先级为 reject > manual > suspect > pass；除明确短路外保留命中集合供解释。只有能映射到内置制度的规则展示条号，不为 R0、R1、R2、R6、R7 编造引用。规则阈值和条款属于样例报销制度，不是税务法律判断。当前 R4 以开票日估计时效，住宿按一晚比较标准；缺少实际出差结束日、住宿晚数等上下文时需要人工核对。

### 4.5 制度问答与工具编排

制度问答采用本地关键词及双字特征检索，筛选相关条款后提供给文本模型；目前没有向量数据库或 embedding 检索，不能把它描述成已落地的向量 RAG。未命中时说明制度未作规定；文本模型不可用时回退原条款摘录。生成后校验引用条号是否在证据范围内，但这不等于完成逐句语义事实验证。

可选 Function Calling 允许模型调用 check_duplicate、search_policy、get_threshold，最多 3 轮。工具读取实际台账、制度及阈值；超时或失败回退固定顺序并记录。它展示可观察的工具决策过程，规则主链仍是结论唯一权威，因此不能声称模型自主批准报销。

## 五、核心功能实现与创新点

### 5.1 上传、进度与失败恢复

UploadDropzone 对选择与拖拽执行统一预检：JPG/PNG/WebP、20 张上限、单张 20 MB、非空文件。文件先进入选择列表，用户可查看总大小、删除，再点击开始审核。提交时禁用重复操作，错误保留选择，便于重试而无需重新选全部文件。

后台将上传接收与逐张处理分开。结果页维护已完成数量和失败列表；partial 时继续呈现成功项，failed 时明确没有可用结果。按原文件名保留失败原因，并对模拟来源提示结果与票面无关，减少“上传了自己的票却读成别人的商家”的误解。

### 5.2 人工复核与汇总一致性

详情页要求用户确认已核对原图并填写理由后改判。每次变更形成一条记录，保留原始机器结论。列表、详情和看板以当前有效结论计算数量；修复过的四类计数不同步问题由相关测试约束，金额合计及处理失败清单保持原有语义。

复核不是自动补开发票，也不证明票据合法。演示时必须说清实际改动了什么，不能把临时演示动作解释成已完成外部业务手续。复核操作者目前是填入的文本，尚未与企业认证系统绑定。

### 5.3 前端表现与可访问性

项目介绍页以发票地图讲解字段与证据：初始桌面票据缩放展示，滚动到标注阶段切换正视票面，按图片坐标定位字段，购销双方留空。图群光标跟随、页面切换和上传页整页揭幕采用团队购买源码适配；人物素材替换为发票相关物件。

这些动效用于信息层次与品牌呈现，不参与真实字段识别。上传页支持跳过/Esc、重播、减少动态效果偏好和异常兜底，重播保留已选文件与压缩状态。桌面和手机分别验收，避免画面被裁切、导航不可达或动画覆盖上传按钮。

### 5.4 技术创新点

本项目的创新定位是面向审核场景的工程组合，不宣称发明新模型、OCR 算法或动画库。其一，将字段抽取、确定性规则和可选模型编排分开，失败可定位且不会由旁路模型任意改写结论。其二，缺失标记、来源与缓存状态贯穿接口到界面，建立可核对的证据链。其三，用规则、字段、端到端三个独立口径评估同一系统，能定位“规则正确但读图错误”的风险。

### 5.5 应用创新点

审核输出由单一通过/驳回变成字段、规则、条款、失败原因与复核轨迹的组合。低置信度和缺项被交给人工核实，历史改判仍保留，适合讲解机器辅助与责任边界。介绍页和高频上传操作分离，既保留答辩展示，也减少日常操作的滚动负担。这些改进已体现于页面与接口，不等同于完成真实财务系统上线。
