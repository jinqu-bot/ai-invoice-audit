## 一、作品定位

### 1.1 问题不在识别，在判定

市面上的票据工具几乎都在解决同一个问题：把图片变成结构化字段。这件事今天已经不难——通用视觉模型读一张清晰的电子发票，金额、税号、日期基本不会错。

但财务真正卡住的不是这一步。**一张字段全对的发票，仍然可能不该报。**

抬头是个人、开票日期在三个月前、住宿 1280 元超了标准、票面印的是"有限公可"而不是"有限公司"——这些发票的字段识别统统没有问题，问题在于"该不该报"这个判断。而这个判断原来只存在于老会计的脑子里。

### 1.2 我们的判断

**识别是原料，判定才是产品。**

所以本项目的重心不在"读得更准"，而在"读了之后怎么给出一个能被追问的结论"。具体落成一句话：

> 不是帮你识别发票，是帮你决定这张发票该不该报——而且每个驳回都指得出制度第几条。

一个结论如果指不出依据，它就不是结论，是猜测。评委和财务都不会为猜测签字。

### 1.3 四条设计原则

这四条不是口号，每一条都直接决定了后面某段代码怎么写：

| 原则 | 落到代码上的样子 |
|---|---|
| **结论必须可追溯** | 每条命中规则都携带 `code` / `evidence` / `basis_article` / `basis_text`，前端点得开、页面看得见 |
| **宁可说不会，不许编** | 制度里没规定的规则（R0/R1/R2/R6/R7）依据字段为 `null`，不硬塞条号；问答检索不到条款时直接拒绝回答 |
| **模型只提供字段，不参与判决** | `verdict` 由 `rules.py` 纯函数算出，模型输出再多也不影响结论；Function Calling 是纯旁路 |
| **人必须能推翻机器，且留下痕迹** | 改判必须勾选"已核对原图"，改判理由与前后结论全部入库，不可静默覆盖 |

第二条尤其重要。整个项目里最容易拿分也最容易翻车的就是"AI 会不会瞎编"，我们的做法是把"不会"做成默认行为，而不是靠 prompt 祈祷。

## 二、系统架构

### 2.1 技术栈

| 层 | 选型 | 为什么 |
|---|---|---|
| 后端 | Python 3.10+（本地 3.12、线上 3.10.12）+ FastAPI 0.162 + Pydantic v2 | 类型即契约，`schemas.py` 一份定义同时产出校验、序列化和 Swagger 文档；代码同时兼容两个版本 |
| 存储 | 标准库 `sqlite3`（无 ORM） | 单机演示场景，不引入 SQLAlchemy；建表与查询都在 `db.py`，看得见 SQL |
| 前端 | Next.js 14.2（App Router）+ TypeScript + Tailwind | 服务端渲染首屏快，路由天然对应四个页面 |
| 模型接入 | OpenAI 兼容协议（`services/llm.py`） | 换供应商只改两个环境变量，业务代码零改动 |
| 部署 | nginx + systemd（`deploy/`） | 单机双服务，开机自启、崩溃自拉 |

### 2.2 分层与模块职责

```
routers/          接口层：只做参数校验、调 service、拼响应，不写业务
  ↓
services/         业务层：识别、校验、规则、查重、复核、问答、落库
  ↓
schemas.py        契约层：所有出入参结构唯一来源
```

关键模块：

| 模块 | 职责 | 一句话说明 |
|---|---|---|
| `image.py` | 指纹、压缩、base64 | 手机照片统一缩到长边 1024，体积与延迟一起降 |
| `llm.py` | 模型调用 + 无密钥时的 mock | 只认 OpenAI 兼容协议 |
| `extract.py` | 抽取编排 | 重试、置信度、缓存都在这一层收口 |
| `validators.py` | 四道关 | 格式 / 算术 / 常识 / 把握 |
| `rules.py` | 规则引擎 R0–R8 | 产出租 `verdict` + 依据条款，纯函数 |
| `policy.py` | 制度条款库 | 规则引用的原文从这里取，不写死在规则里 |
| `policy_qa.py` | 制度问答 | 检索 + grounded 校验 + 三级降级 |
| `agent.py` | Function Calling 旁路 | 让模型自己决定查什么，但不许改结论 |
| `reviews.py` | 人工复核 | 改判 + 留痕轨迹 |
| `history.py` | 报销台账 | 查重依据，按来源分区 |
| `store.py` / `db.py` | 存取与落库 | 批次、发票、复核记录 |
| `runner.py` / `jobs.py` | 批次后台任务与事件总线 | 逐张审、逐张推事件 |
| `model_health.py` | 模型健康度 | 记录最近成功时间与连续失败次数 |

### 2.3 一次上传的完整时序

```
浏览器 ──POST /api/batches (multipart)──► 后端
                                            │ 1. 存原图、算 sha256 指纹
         ◄──── 202 {batch_id, processing} ──┤ 2. 立刻返回，不等模型
                                            │
        ◄──── SSE: hello ───────────────────┤ 3. 建立进度流
                                            │
                                    后台任务 runner
                                            │ 4. 逐张：压缩 → 抽取 → 四道关 → 规则
        ◄──── SSE: invoice_done ×N ─────────┤ 5. 每审完一张推一张
        ◄──── SSE: batch_done ──────────────┤ 6. 整批结束
                                            │
        断流了也不怕：GET /results 可随时补拉
```

**为什么要 202 + SSE，而不是同步返回？** 五张票要等二三十秒，在这期间浏览器只能转圈。转圈的二十秒在演示里就是死掉的二十秒。改成"先收下、边审边推"之后，第一张结果通常在一两秒内出现，观众能看见进度在动。

同理，SSE 断流不能让结论丢失——结果早已落库，`GET /api/batches/{id}/results` 在 `processing` 期间也能调用。**流只是展示，不是数据源。**

### 2.4 三个架构决策与理由

**① 结论由规则算，不由模型给。**
早期版本让模型直接输出"通过/驳回"，问题是同一个 prompt 两次跑可能给两个结论，而且给不出条号。改成模型只出字段、规则出结论后，同样的输入必得同样的输出，且每条结论都能追到条款。**可复现是可审计的前提。**

**② 一张失败不拖垮整批。**
批次里每张票独立处理，异常被捕获进 `failures`，写清文件名与错误码（如 `BAD_IMAGE`）。观众看到的是"4 张成功、1 张坏文件"，而不是整页 500。

**③ 密钥只从环境变量读。**
`config.py` 自己解析 `backend/.env`，不依赖 python-dotenv，且**真实环境变量优先级高于文件**——临时换模型在命令行给值即可。`.env` 进 `.gitignore`，仓库只提交 `.env.example`。

## 三、AI 技术方案

### 3.1 识别链路：五步

```
上传 → 压缩 → 模型抽取 → 四道关 → 置信度闸门 → 结论
        ↓         ↓          ↓           ↓
     指纹去重   严格 JSON   错误回灌重试   低于阈值转人工
```

任何一步不过关，这张票就转人工（`manual`），而不是硬着头皮往下走。

### 3.2 Prompt 三条铁律

```
每个字段都必须来自图片像素，看不清就填 null
严禁根据常识补全或推算金额
每项都要给 confidence，表示你在这项上的把握
```

第一条和第二条是防"纠错式误读"的。数据集里 ds_004/ds_005 两张票，票面**故意**印着"有限公**可**"——模型看到之后，会有很强的倾向把它"纠正"成"有限公司"。这不是模型笨，是它太想帮忙。铁律是拦不住的（实测确实没拦住，见 7.3），但它是这条链路上第一道防线，后面还有规则层和人工复核兜底。

### 3.3 四道关

| 关卡 | 拦什么 |
|---|---|
| 格式关 | 必填字段在不在、类型对不对 |
| 算术关 | 不含税 + 税额 ≈ 价税合计（±0.01） |
| 常识关 | 日期不能是未来、税号位数、税率合法性 |
| 把握关 | 关键字段置信度太低就转人工 |

算术关是重中之重：价税勾稽是模型最爱翻车的地方，也是最容易用一行减法验出来的地方。

### 3.4 置信度取最小值，不取平均

五个关键字段，四个 0.99、一个 0.3，平均值 0.85 看着挺好，但这张票实际不该被信任。

**取最弱的那一项，才诚实。** 这是全项目最便宜也最有效的一个决定——它让"整体把握 30%"的票自动落到 R0 转人工，而不是被平均分掩盖成一张正常票。

### 3.5 错误回灌重试

前两关（格式关、算术关）报错时，错误信息会**回灌给模型**，并且只让它改错的那几处，而不是整张重来。这样既保住了其余字段的稳定性，又能修掉勾稽不平这类确定性问题。

### 3.6 供应商无关

只认 OpenAI 兼容协议。Qwen-VL / GPT-4o / 豆包 / 本地 vLLM 都能接，换供应商只改 `.env` 里的 `base_url` 和 `model`：

```bash
# backend/.env
VLM_API_KEY=sk-xxxx
VLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
VLM_MODEL=qwen-vl-max
```

代码一行不动。这个约束不是为好看——它意味着**评测结论不被单一供应商绑架**。

### 3.7 没有密钥时的降级：不假装成功

没配 `VLM_API_KEY` 时自动降级到 mock 提供者，链路照跑，但响应里的 `provider` 明写 `mock-vlm`，前端也以"演示数据"标注。

这不是"假装 AI 成功"，是让压缩、校验、重试、缓存、前端联调在没有密钥时也能被完整验证。**能力边界必须写在响应里，而不是写在文档里等人去查。**

线上健康检查同样遵守这条：`/api/health` 不只报"有没有 key"，而是报 `model_ok`、`last_ok_at`、`last_error`、`consecutive_failures`。这条是踩坑换来的——曾经账户欠费时健康检查照样返回 ok，录演示时才发现模型根本调不通。

### 3.8 Function Calling：让模型自己决定查什么（但不许改判定）

这一层是**旁路**，不影响任何结论。三个真实工具：

| 工具 | 作用 |
|---|---|
| `check_duplicate` | 查这张票是否已报销过 |
| `search_policy` | 检索制度条款 |
| `get_threshold` | 取某类目的费用上限 |

模型可以在最多 3 轮内自行决定调用顺序与次数；模型不可用时退回固定顺序 `check_duplicate → search_policy`，响应里用 `by=model` / `by=fallback` 明确区分，没有真实模型时直接返回 503 **而不是假装调用过**。

线上实测（`verification/agent-plan-live.json`）：模型自主选择了「查重 → 取费用上限 → 检索条款」三步，全部 `by=model`、`fallback=false`、耗时 5.4 秒，并自行走到第 8 条得出驳回结论。

**但它漏掉了 R4 超期。** 这个结果我们原样保留在文档里——它恰好证明了为什么规则引擎必须保持权威：模型的推理路径不可穷举，规则的覆盖面可穷举。

### 3.9 制度问答：检索 + grounded 校验

问答不允许自由发挥，流程是三步：

1. **检索**：按问题分词打分，取最相关的 3 条条款；
2. **生成**：把条款原文连同问题一起给模型，要求只依据条款回答；
3. **回头校验**：生成完再检查它引用的"第 X 条"是否真在检索结果里，不在就标记 `grounded=false` 并给出警告。

三级降级，每一级都比"编一个像答案的答案"诚实：

| 情况 | 返回 | `provider` |
|---|---|---|
| 检索不到条款 | 明确说"制度里没有相关规定，建议咨询财务" | `rules-only` |
| 模型不可用 | 只摆条款原文，不生成结论 | `retrieval-only` |
| 正常 | 模型生成 + grounded 校验 | `openai-compat` |

### 3.10 识别缓存

同一张图第二次进来直接命中缓存，毫秒级返回，响应里带 `cached=true`，前端在卡片和详情页都标"识别缓存命中"。

演示时它是双刃剑：网络抖动时它是救命稻草，但它证明不了"模型此刻真的在读图"。**所以我们把它标出来，而不是藏起来。** 需要演真识别时用 `reset_demo.py --yes --flush-cache` 清缓存。

## 四、规则引擎与判定

### 4.1 R0–R8

| 规则 | 名称 | 结论级别 | 制度依据 |
|---|---|---|---|
| R0 | 识别置信度不足 | manual | —（制度未规定，如实留空） |
| R1 | 重复报销 | reject | —（内部台账约束，非制度条款） |
| R2 | 关键要素缺失 | manual | — |
| R3 | 抬头或税号不符 | reject | 第 8 条 |
| R4 | 超期提交 | suspect | 第 15 条 |
| R5 | 超出费用标准 | suspect | 第 12 条（住宿）/ 第 5 条（招待） |
| R6 | 明细与合计不符 | suspect | — |
| R7 | 税率或税额异常 | suspect | — |
| R8 | 敏感类目 | suspect | 第 9 条 |

条款原文存在 `policy.py` 引用的制度库里，规则本身只保存 `doc_id + article_no`，**原文不写死在规则里**。这样改制度只改一个地方，而且能保证"页面上显示的条款"和"判定时依据的条款"是同一份文本。

### 4.2 优先级与短路

```
reject (3) > manual (2) > suspect (1) > pass (0)
```

一条票可能同时命中多条规则，最终结论取最高的那一级，但**所有命中都会完整列出**——驳回理由不能只给一条，财务需要知道全部问题。

R1（重复报销）是唯一会短路的规则：一旦命中，后续规则不再执行。理由很实际——**已经报过的票，再分析它的住宿标准没有意义**，而且短路能省掉一整轮条款检索。

### 4.3 依据条款：有就带，没有就 null

R0/R1/R2/R6/R7 这五条在制度里找不到对应条款，它们的 `basis_article` 就是 `null`。

这是刻意的。给 R1 硬塞一个条号，页面上看起来更"完整"，但那是编的。有一条测试专门钉死这个约束（`test_每次命中都带出自己的依据条款`）——以后谁想给 R1 塞条号，测试会红。

### 4.4 为什么规则引擎是权威

因为**它能被穷举，而模型的推理路径不能**。

我们已经用实测证明了这一点：3.8 里那个自主规划的模型，独立走到了第 8 条并给出驳回，看起来很像人——但它漏了超期。如果结论由它决定，这张票就会被判"驳回"而不是"驳回（超期 + 抬头不符）"，财务拿到的依据就不全。

所以分工是死的：**模型负责"看见"，规则负责"判断"，人负责"推翻"。**

### 4.5 查重与台账分区

查重依赖报销台账，台账按来源分区：演示批次（fixture）与真实审核记录分开存放。

这个设计是被一次事故逼出来的——早期演示批次的票混进了真实台账，导致新上传的票误判成"重复报销"。分区之后，`?demo=true` 的数据只和 demo 数据比对，真实审核只和真实台账比对。

## 五、核心功能实现

### 5.1 四态结论

| 结论 | 含义 | 颜色语义 |
|---|---|---|
| `pass` | 通过 | 绿 |
| `suspect` | 存疑，需补充说明 | 黄 |
| `reject` | 驳回 | 红 |
| `manual` | 转人工 | 灰 |

四态而不是二态，是因为**"说不清"本身就是一种需要被表达的结果**。把置信度不足的票强行归入通过或驳回，等于假装系统什么都懂。

### 5.2 证据链

每张票的详情页可以逐层下钻：

```
结论 reject
  └─ 命中 R3（抬头或税号不符）
       ├─ evidence: { actual_name: "…", expected_name: "杭州云帆科技有限公司" }
       ├─ basis_article: 第 8 条
       └─ basis_text: "报销发票的购买方名称及纳税人识别号必须与公司登记信息完全一致……"
```

字段 → 规则 → 条款，三段都能在页面上点开看到原文。**评委追问"凭什么"的时候，答案在屏幕上，不在主讲人嘴里。**

### 5.3 人工复核

改判必须满足两个条件，缺一不可：

1. **勾选"已核对原图"** —— 不让人随手改判；
2. **填写改判理由** —— 理由必填，且与前后结论一起入库。

每次改判生成一条独立记录（原结论、新结论、理由、时间、操作者），**不覆盖原结论**。轨迹页能看到完整的变更历史。

这条约束在演示里有个副作用是加分的：故意不勾选就提交，会被拦住。这不是 bug，是设计。

### 5.4 制度问答

`/ask` 页面左侧是检索到的条款原文，右侧是模型回答。模型答完之后，页面会标出哪些条款被引用、是否 grounded。

问一个制度里没有的问题（比如"年会抽奖怎么报"），它会明确回答"现行制度里没有找到相关条款"——**这是整个演示里最该给评委看的一条。**

### 5.5 审核看板

看板读的是数据库里的真实聚合（`store.dashboard_month`），空库时才退回演示样例，并在响应里用 `source="fixture"` 标明来源。

**不能让看板显示一批"库里根本没有"的漂亮数字。**

### 5.6 前端工程约束

1. 所有请求走 `src/lib/api.ts`，页面里不写裸 `fetch`；
2. 后端字段变了，`src/lib/types.ts` 必须同步改（与 `schemas.py` 一一对应）；
3. 结论颜色统一用 `VERDICT_META`，不自己挑颜色。

三条约束的目的只有一个：**结论颜色的语义不能在不同页面漂移**。绿色在结果页是"通过"，在详情页也必须是通过。

### 5.7 部署与运维

单机 nginx + 两个 systemd 服务：

```
nginx :80
  ├─ /       → 前端 Next.js :3100
  └─ /api/   → 后端 uvicorn :8000
```

配置里最容易翻车的是 SSE 那三行：

```nginx
proxy_buffering off;
proxy_cache off;
proxy_read_timeout 3600s;
```

`proxy_buffering off` 删掉，"实时进度"就会被 nginx 攒成一坨、最后一起吐出来——看起来像后端变慢，其实是反代在缓冲。前端用相对路径 `/api/*`，因此浏览器只看到一个 origin，不涉及跨域。

运维侧有三件东西：`/api/health` 报模型真实可用性、`reset_demo.py` 一键复位演示环境（可选同时清缓存）、批次重启不留僵尸状态。前端构建必须用 `NEXT_PUBLIC_API_BASE=`（相对路径），否则换 IP 就要重新构建。

### 5.8 安全与隐私

| 项 | 做法 |
|---|---|
| 密钥 | 只从环境变量读，`.env` 不进仓库，仓库只提交 `.env.example` |
| 真实票据 | 含个人姓名税号的真实发票**不进 Git、不上服务器**；公开材料用程序生成的样票 |
| 演示数据 | mock 与演示批次在界面上明确标注，不与真实识别结果混淆 |
| 文档中的姓名 | 全仓库统一使用占位名，与真实持有人无关 |

真实票据这条值得单独说。演示用的那张真发票上有第三方的姓名和税号，现场口头讲没有问题，但**提交的视频是公开材料**。所以我们另做了一张"个人抬头 + 超期"的样票（购买方写「个人用户」，无税号），线上实测命中 R3 + R4、结论 reject，与真票的叙事完全一致，台词都不用改。

## 六、测试数据集构造

可信的评测始于可信的数据。本项目构建了一套 **60 张、零隐私、可完全复现** 的合成测试数据集（`backend/data/dataset/`，附 `ground_truth.json` 逐条标注），构成如下：

| 构成 | 张数 | 说明 |
|---|---|---|
| 合成票 · 干净渲染 | 12 | Pillow 按增值税电子发票版式渲染的基准样本（其中 9 张为规则埋雷母票） |
| 合成票 · 增广 | 23 | 在干净票施加噪点、±3°–8° 旋转、半透明折痕带，模拟拍摄退化；增广子票继承母票字段、发票号码唯一化 |
| 合成票 · 转人工样例 | 3 | ds_036 发票号码区域留白（缺号码型 R2）、ds_037 金额三件套缺失（缺金额型 R2）、ds_038 关键区域马赛克（低置信度 R0） |
| 实拍票 | 12 | 打印合成票 → 手工折叠（3）/ 揉皱（6，含全数据集最重的 real_12）/ 平拍（3）→ 手机拍摄，含闪光灯与顶灯光照样本 |
| 非发票 | 10 | 聊天截图、手写收据、课堂投影、风景街景等负样本（其中 2 张为程序生成：微信界面风、收据风） |

**埋雷设计**：规则引擎 R1–R8 每条规则配 1–2 张专用触发票（如 R1 重复报销对预置台账号码 66472890、R5 住宿 1280 超 800 标准、R7 住宿 13% 异常税率、R8 敏感词"烟/酒水"），保证"每条规则都有且仅有对应的测试弹药"。`ground_truth.json` 逐条携带 `expected_verdict`、`hit_rules` 与评测基准日 `eval_date = 2026-11-06`。

**可复现性**：`make_dataset.py` 固定随机种子 20261106，全量重跑结果逐字节一致；`make_to_print.py` 输出打印素材，按"打印 → 折叠/揉皱 → 手机拍摄"流程即可重现实拍批次。数据集构建与评测脚本共 3 个，全部入库。

## 七、测试与评测

后端共 **170 项 pytest，全绿**。测试体系分三层，各自回答一个不同的问题：

### 7.1 数据层一致性（13 项 pytest 全绿）

`backend/tests/test_dataset.py` 校验：60 张图与标注一一对应、金额勾稽（不含税+税额=价税合计，±0.01）、类目-税率合法性、雷型分布与 verdict 分布对拍、R2 样例字段缺失标记、号码唯一性、eval_date 全覆盖。**这一层保证"标注说的和图印的是同一件事"**——11 月 7 日曾靠这层测试抓到"R3 错字只改了标注没改进图"的哑雷，避免其流入正式评测。

### 7.2 规则口径对拍：60/60

将 `ground_truth.json` 字段原样注入规则引擎（不经 OCR），独立样本与整批两种模式均 **60/60 全对**（`docs/对拍结果.md`，`eval_dataset.py` 可复跑）。**该口径只证明"规则与标注说同一件事"，不含任何识别成分，不作为识别成绩引用。**

### 7.3 真识别与端到端（核心成绩）

- **识别字段（11 字段）**：`verification/recognition-11-fields-60.md`。**50 张发票图（38 合成 + 12 实拍），全对 44/50、字段级 544/550 = 98.9%**（真实视觉模型经 openai-compat 接口调用，模型 ID 见运行配置；金额容差 0.01；缺失与失败保留在分母）。分组：实拍 11/12、原样 11/14、加噪 9/10、旋转 8/8、折叠 5/5、低置信 0/1——**退化增广下字段识别基本不衰减，数字类字段（金额/号码/日期/税号/税率）零错误**，错误集中在文字理解与类目主观判断。

- **端到端**：`verification/end-to-end-60.md`，真模型读图 → 规则引擎 → 结论，与标注逐票对比（每张票独立台账，避免增广票号码撞车把查重能力误测为准确率）。**60 张中结论一致 56/60 = 93.3%**，命中规则集合一致 54/60；按期望结论 pass 34/35、suspect 9/9、reject 1/3、manual 12/13。

- **错例分析（方向比数量重要）**：四个错例中 ds_004、ds_005 为**危险方向**（票面故意错字"有限公可"被模型高置信"纠正"为"有限公司"，R3 未拦住，同一形近字病灶）；real_06（年份 6→4 多报超期）与 ni_10（非发票被编出金额判驳回）为**保守/偏严方向**。该分布支撑设计决策：识别层易犯的"纠错式误读"由规则层与人工复核兜底（见 5.3），而非依赖置信度阈值。

### 7.4 评测口径纪律

全项目数字收敛为三个，各有出处、互不替代（`docs/评测口径总表.md`）：规则 60/60（非识别）、识别 544/550（98.9%）、端到端 56/60（93.3%）。任何引用必须带样本数、口径与模型；40/40、58/58、92.5%、55/60 等旧口径数字已全部作废。数据集更新（40→58→60 张）后所有评测均重跑定格，杜绝"一套旧数字吃到底"。

### 7.5 已知边界

样本来自同一虚构公司、同一打印机与拍摄者，统计结论不构成对任意真实票据识别效果的承诺；低置信度样例仅 1 张，转人工路径的识别侧覆盖率有限，已列入后续工作。

另有两条实测出来的边界，一并写在这里：

- **受票人姓名读取不稳定**：同一张票多次运行，模型可能给出不同姓名（实测出现过四种读法），发票号码也出现过 18 位 / 20 位两种长度。这不是"稳定读错"，而是**每次都可能不一样**——所以姓名类字段必须人核。
- **模型自主规划会漏规则**：Function Calling 旁路能自主走对推理路径，但实测漏掉了 R4 超期（见 3.8）。这是规则引擎保持权威的直接理由，不是理论推演。

## 八、总结与展望

### 8.1 总结

本项目完成了一个"判定优先"的智能报销审核系统：模型负责从像素中读出字段，规则引擎负责给出可追溯到制度条款的结论，人负责推翻机器并留下痕迹。围绕这一架构，我们交付了三样可以独立存在的东西：

- **一套双引擎审单架构**——LLM 编排与确定性规则各司其职，结论可复现、可审计，模型推理路径不可穷举的问题由可穷举的规则覆盖面兜住；
- **一套零隐私、可完全复现的评测体系**——60 张合成数据集（程序渲染 + 打印拍摄）、埋雷式规则验证、三层测试与全量对拍，评测数字经两轮收敛后全项目唯一口径；
- **一套诚实的失败记录**——形近字误读、模型漏规则、姓名读取抖动，全部写入文档而非藏进脚注，并逐一给出工程缓解。

### 8.2 展望

- **制度检索从关键词升级为向量检索**：当前停用词表方案在制度条款增长到数百条时会出现匹配漂移，引入 embedding 检索 + 重排是自然的下一步；
- **接入登录与权限体系**：人工复核目前靠"自觉留名"，真实落地需对接 SSO，并按角色区分改判权限；
- **打通申诉闭环**：目前是财务在后台改判，理想形态是"驳回 → 报销人申诉 → 财务复核"的双向流程；
- **识别置信度与规则联动深化**：票面要素放大复核（默认关闭）与发票号码自校验已部分落地，下一步可将"字段级置信度"纳入规则引擎的决策输入，而非仅作为整体闸门；
- **更大规模的真实世界验证**：60 张样本验证了方法可行性，统计意义上的稳健性需要跨打印机、跨拍摄设备、跨版式的更大样本，这也是从演示走向产品的最后一段路。
