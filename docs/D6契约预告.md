# D6 契约预告：上传改成「先返回、后台再跑」

> A（后端）· 2026-11-07 · **按我们说好的规矩，契约变更提前通知**
>
> 一句话：**`POST /api/batches` 不再等审核跑完才返回**，改成立刻返回 `202` + 批次号。
> 你那边**只有一处必须改**（判断状态码的地方），其它都是新增、可选。

---

## 一、为什么改

现在 `POST` 要等全部识别完才返回：5 张票要等 8–10 秒，浏览器就干等着，
进度流其实是"跑完了把录像播一遍"。答辩时被问"这是真的实时吗"，只能如实说不是。

改完之后：

1. `POST` 立刻返回（几十毫秒），页面立刻跳结果页；
2. 结果页订阅 `/stream`，**每审完一张就推一张**，进度是真进度；
3. 单张失败（截图、坏文件）当场推 `file_failed`，不用等整批。

---

## 二、必须改的地方（只有这一处）

`POST /api/batches` 的状态码从 **200 → 202**。响应体形状完全不变，只多一个取值：

```json
{
  "batch_id": "B20261107-001",
  "invoice_count": 3,
  "created_at": "2026-11-07 16:20:31",
  "status": "processing",
  "failed": [],
  "next_action": "/api/batches/B20261107-001/results"
}
```

`status` 现在有四个值：`processing` / `done` / `partial` / `failed`。

**你的代码里如果写了 `if (res.status === "done")` 之类的判断，要放宽成"不是 processing 就是结束"**。
如果只是拿 `batch_id` 跳页，一行都不用改。

> `?demo=true` 仍然是 **200 + `status=done`**（演示批次是现成的，没什么可等的）。
> 所以：**`202` 表示"要等"，`200` 表示"已经好了"**。按状态码分支最省事。

---

## 三、新增的东西（不接也能跑）

**1. SSE 多了两种事件**

```
event: batch_start
data: {"batch_id":"B20261107-001","total":3}

event: file_failed
data: {"filename":"WeChat截图.png","code":"BAD_IMAGE","message":"不是图片文件…"}
```

原有的 `invoice_start` / `trace` / `invoice_done` / `batch_done` **一个都没变**，
所以你现在的订阅代码能直接跑，只是会更早收到事件、并且是真实的。

**2. `GET /results` 在 `processing` 期间可用**

返回已经审完的那几张，`batch.status = "processing"`，`items` 会一张张变多。
**这是你的兜底**：万一 SSE 断了（代理、断网、企业防火墙），
每秒打一次 `/results`，等 `status != "processing"` 就是结束。**建议就按这个做兜底**，
现场网络不可靠，SSE 挂了页面不能跟着挂。

**3. 批次列表里会出现 `status=processing` 的批次**，别把它当失败。

---

## 四、几个边界情况，先说清楚

- **后端中途重启**：正在跑的批次会被标成 `failed`，并在 `failures[]` 里写"服务重启，本批中断"。
  不会永远停在 `processing` 让页面转圈——这是刻意的。
- **`processing` 期间 `/results` 的 `items` 数量小于 `invoice_count` 是正常的**，
  别用 `items.length` 判断总数，用 `batch.invoice_count`。
- **同一批次重复订阅 `/stream` 没问题**：会从头补发一遍已有事件再接着直播，
  页面刷新之后不需要特殊处理。
