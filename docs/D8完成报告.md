# D8 完成报告 · 人工复核

> 2026-11-08 · A（后端）· 已上线 `http://8.217.202.172`

## 为什么做这个

R0–R8 全是机器判断，机器**一定会判错**：抬头识别糊了一个字、金额小数点错位、
或者这张票本身就特殊。如果系统只有"驳回"没有"改判"，它就是一台不讲理的机器——
用户拿着合规的票被拒，只能去吵，而系统里没有任何东西能证明谁对。

这个接口定的是：**机器看错时，人的判断怎么覆盖它，以及这次覆盖留下了什么痕迹。**

答辩时"判错了怎么办"这个问题的答案，就是这一页。

---

## 做成了什么

### 接口

```
POST /api/invoices/{invoice_id}/review
{
  "action": "pass | suspect | reject | manual",   // 改判成什么
  "reason": "抬头已补开，财务确认可报",             // 必填，至少 2 字
  "reviewer": "张会计",                            // 可空 → 记“未登记”
  "note": ""                                       // 补充说明
}
```

三条底线：

1. **理由必填**——没有理由的改判等于没留痕，Pydantic 层直接 422 拦掉
2. **只能改成那四种结论**——不发明新状态，跟机器用的是同一套词
3. **原结论一并记下**——只写"现在是 pass"没用，得知道"之前机器说是 reject"

### 留痕

新表 `reviews`：谁、什么时候、从什么改成什么、凭什么。同一条轨迹可累积——
改判两次能看到"张会计 suspect→pass，李主管 pass→reject"，谁的责任一目了然。

### 一致性

列表页和详情页用的是同一份覆盖逻辑（`reviews.apply_many`），
**不会出现"详情说通过、列表还显示驳回"这种打脸现场**。

### 前端

详情页新增「人工复核」面板：四个按钮选结论、理由输入框、复核人输入框、
提交后原地刷新（不用手动重载），下方是改判轨迹时间线。

## 验收（线上实测，不是本地）

```
复核前   INV-0004 | suspect | 超出住宿标准 480 元，需总监审批
空理由   → 422（拦住了）
改判     → 200 | pass | 人工复核通过：抬头已补开，财务确认可报
轨迹     1 条：suspect → pass · 张会计
列表页   pass | reviewed=True          ← 和详情一致
二次改判 → reject，轨迹 2 条：
         21:29:26 张会计 suspect→pass
         21:29:26 李主管 pass→reject
```

后端测试 **123 项全绿**（新增 6 项复核测试），前端 typecheck + build 通过。

---

## 一个踩到的坑

第一次写"两次改判"的测试是红的：时间戳只到秒，同一秒内改两次时
`ORDER BY decided_at` 无法区分先后，第二次改判反而被第一次盖住。
改成按 `rowid`（插入顺序）排序才对。**这类"看着对、顺序错"的 bug 只有写成测试才会暴露。**

---

## 还没做的

- 复核目前**没有权限控制**（`reviewer` 是自由填写的字符串）。
  没有登录体系，这只能是"自觉留名"。真上线必须接 SSO。
- 没有"申诉"入口：现在是财务在后台改判，报销人自己不能发起申诉。
  演示够用，但真正的闭环应该是"驳回 → 报销人申诉 → 财务复核"。

# 附：制度问答（D8 的另一半）

## 做了

`GET /api/policies/ask?q=...` → 检索条款 → 只依据条款回答 → 校验引用。

三道闸，防的都是同一件事：**答得太顺**。

1. **检索不到就说没有**。制度里 6 条，问"加班费怎么算"必须答"制度未作规定"，
   而不是硬凑一条。第一版按"任意二字命中"检索，
   "公司年会抽奖怎么报销"也能匹配上——因为"公司""报销"每条制度里都有，等于没有区分度。
   现在按文档频率剔高频词、要求命中至少一个"只属于某一条"的词，并加了一张手写停用词表。
2. **只允许用传进去的条款作答**，提示词里写死，禁止常识补全。
3. **生成完回头查它引用的「第 X 条」在不在检索结果里**，不在就标 `grounded=false`
   并在页面上红字提示"这条回答不可信"。

## 线上实测

```
住宿费超标了还能报吗   → 超标部分经部门总监审批后可报（第12条）        2042ms
发票抬头写错了能报吗   → 不能，购买方名称须与公司登记一致（第8条）      2907ms
出差回来多久内要交票   → 30 日内，逾期附说明（第15条）                2308ms
加班费怎么算           → 制度里没有相关条款，建议咨询财务（refused）      0ms
```

前三条 `grounded=true`、引用条号全部真实存在；第四条直接拒答。

## 降级

没配文本模型、或模型超时/报错时，**不生成结论**，只把检索到的条款原文摆出来，
`provider=retrieval-only`。这比编一个看着像答案的答案诚实。

## 已知局限

检索是关键词 + 停用词表，不是向量检索。语料 6 条够用，
涨到几百条会出现"办公用品"匹配到"办公室空调"这种偏差。真要上线得换 embedding + 重排。
