## 二、改了什么

### 1. 上传拆成两段（契约变更，已提前通知 B）

| 之前 | 现在 |
|---|---|
| `POST` 等全部审完，200 + `done` | `POST` 立刻返回，**202 + `processing`** |
| 前端干等 1.3 秒（5 张更久） | 16ms 返回，跳页，边看边等 |
| `/stream` 回放存好的轨迹 | `/stream` 推真实发生的事件 |

`?demo=true` 保持 **200 + `done`**：演示批次本来就是现成的，没必要装成"正在审"。
**202 = 要等，200 = 已经好了**，这个区分比统一成 202 更好懂。

### 2. 批次"边跑边存"

批次在 `processing` 期间就落库了，`/results` 能查到已经审完的那几张。
这带来两个好处：

- 前端能拿它当 SSE 的兜底（现场网络断了照样出结果）；
- 用户刷新页面不会看到空白——已经审完的还在。

实现上是把 `build_batch()` 拆成 `create_batch()` → `add_invoice()` → `finish_batch()`。
汇总数字在收口时**从库里重算**，而不是一路累加——累加漏一次就永久错。

### 3. 后台任务用线程，不用 `asyncio.create_task`

这是踩出来的：任务挂在请求的 event loop 上，**任何"请求结束就回收循环"的部署方式
都会把批次悄悄掐死**，表现是永远转圈（我们的测试客户端就是这么坑的）。

改成独立线程 + 自己的 loop，批次寿命和请求彻底解耦。代价是事件总线要线程安全
（`Condition` + 轮询取事件，30ms 一次，事件频率低到看不出延迟）。

### 4. 重启不再留僵尸批次

启动时扫一遍 `status='processing'` 的批次，标成 `failed`，
并在 `failures[]` 里写"服务重启，本批中断；已完成的发票仍可查看"。

**一个永远转圈的批次，比一个明确失败的批次糟得多。** 这句话写进测试注释了。

### 5. 前端结果页重写

- 骨架屏数量用 `batch.invoice_count`（processing 期间 = 待审张数），**不能用 `items.length`**；
- 收到 `invoice_done` 就刷一次 `/results`——SSE 只负责说"有变化"，数字只信接口，避免两套状态打架；
- 同时开 1 秒轮询，SSE 挂了也照样走完；
- 正在审的那张显示缩略图 + 当前步骤（"抬头校验…"），比纯骨架屏有说服力；
- `hello.replay` 为真时页面上标「回放」——**不能把回放当实时摆着**。

## 四、现场验收时当场发现的两个问题（已修）

改完先自己跑了真实 HTTP，抓到两个只有真跑才会暴露的毛病：

**1. `processing` 期间 `invoice_count` 是 0，页面摆不出骨架屏。**

`create_batch()` 把张数写成了 0，等收口才填实际张数——于是页面打开时
`total = 0`，进度条和骨架屏全都不出现，直到第一张审完才"砰"地冒出来。
看着像卡住。

改法：建批次时就把**待审张数**写进 `invoice_count`，读取时取
`max(库里的张数, 已落库卡片数)`。收口时改成实际张数（有文件失败会变少）。
现在 POST 返回的 `count=2`，响应回来那一刻页面就有两个骨架屏。

**2. 侧边栏还写着「当前阶段：D1 · 数据为演示样例」。**

这是最不该留的东西：整个页面在做真审核，角落里却在说自己是假的。
改成「D6 · 规则引擎 R0–R8 · 结果落库 · 进度实时」，并如实标注
「识别走 mock（未接真模型 key）」。

**教训**：文档里写的"已完成"，和用户在屏幕上看到的东西，是两件需要分别验证的事。

## 五、这一版仍然不是"实时"的地方（必须说清）

1. **单张内部的 11 步轨迹是一次性推完的**。因为除模型调用外每步都是毫秒级，
   真按耗时推就是"刷"一下全出来。整批进度是真的，单张内部是审完即发。
2. **历史批次、演示批次走回放**，响应里 `replay=true`，页面标「回放」。
   这一路本来就该是放映，只要别冒充实时就行。
3. **识别本身还是 mock**（没有真模型 key）。所以"400ms 一张"是 mock 的耗时，
   真模型接上后会变成 1–3 秒——**到那时进度会更明显，也更需要这一套**。

### 部署前提（别踩）

- **后端只能单进程跑**（`uvicorn` 默认就是）。任务和事件在进程内存里，
  多 worker 会把"上传"和"订阅"分到不同进程，SSE 永远等不到事件。
  真要多副本，事件得挪到 Redis 之类——这次不做，但要知道边界在哪。
- 事件缓存只留**最近 50 批**，更早的批次走库里轨迹回放（内容完整，
  只是没有 `batch_start` 那条"这批共几张"的开场）。
- 后台线程是 daemon：进程退出时批次会被打断，下次启动由
  `recover_interrupted()` 收尾成 `failed`。
