## 一、三件事，按重要性排

### ① 台账落库（这条最重要，本来是"功能假实现"）

D4 的 R1 重复报销，靠的是内存里的一个字典。这意味着：

> 传一张票 → 判"通过" → **重启后端** → 再传同一张 → 还是"通过"。

一条"重复报销"规则，被一次重启就能绕过去。**这不算实现，只算演示。**

现在台账写进 SQLite，重启后同一张票仍然判 `reject / R1`。
测试里专门有一条叫 `test_duplicate_detected_across_restart`：
传一次 → `db.close()`（等于进程重启）→ 再传一次 → 必须是红灯。

### ② 部分成功（这条用户感知最强）

以前：一次传 5 张，第 3 张是微信截图 → 整批 502，前两张白等了。
现在：逐张处理，前两张正常入库出结论，第 3 张进 `failed[]`，批次状态 `partial`。

前端拿到的是：

```json
{
  "batch_id": "B20261106-001",
  "invoice_count": 2,
  "status": "partial",
  "failed": [
    { "filename": "WeChat截图.png", "code": "BAD_IMAGE",
      "message": "不是图片文件（只收 JPG / PNG / WebP）" }
  ]
}
```

失败原因码只有四个：`BAD_IMAGE` / `EMPTY_FILE` / `FILE_TOO_LARGE` / `EXTRACT_FAILED`。
**全失败时也给批次号**——这样结果页还能打开，能告诉用户"是哪张、为什么"，
而不是只弹一个 toast 就没了。

### ③ 分页

`GET /api/batches?limit=20&offset=0` → `{total, limit, offset, items}`。

排序是 `created_at` 倒序、同时间按 `batch_id` 倒序。第二个排序键不是多余的：
批次的 `created_at` 只精确到秒，同一秒传两批时不加 tiebreaker，翻页会重复或漏掉。
测试 `test_batch_list_is_paginated` 断言两页的批次号不相交。

## 二、为什么用 sqlite3 而不是 ORM

这个项目的查询就五条：存批次、读批次、存发票、读发票、按天取批次号序号。
引入 SQLAlchemy 会多一层抽象、多一堆依赖、多一个装不上的风险，
而答辩时评委问"数据怎么存的"，标准库的答案更好讲。

图片没有塞进数据库，而是落在 `backend/data/uploads/`，库里只记路径和 mime。
5MB 的图塞 SQLite 也能跑，但备份、排查、清理都会变难，不划算。

## 三、顺带修掉的两个隐性问题

**① 批次号会重号。** 以前当日序号在内存里，重启后从 001 开始，
于是 `B20261105-001` 可能出现两次，`/api/batches/{id}` 直接指向错误的数据。
现在序号存在 `counters` 表里，测试 `test_batch_ids_do_not_repeat_after_restart` 钉住了它。

**② 同批重复上传查不出来。** 台账记账原本放在路由里、整批审完之后才做，
所以同一批里传两张一样的票，两张都能"通过"。现在记账在每张审完时立刻发生，
测试 `test_same_invoice_twice_in_one_batch` 断言第二张必须是红灯。

## 六、已知问题，不装

1. **分页是"假分页"**。演示批次是固定假数据、不入库，为了让它们一直可见，
   列表接口先把库里的批次和演示批次合并，再切片。数据量小（几十条）时没问题，
   上千条时该改成数据库分页 + 演示批次单列。
2. **SSE 仍是"结果回放"**。批次早审完了，进度流是把存下来的轨迹按节奏播一遍。
   真正的实时进度要等 D6 把 `POST /api/batches` 改成"先返回、后台再跑"。
3. **没有登录，台账里的报销人一律写"报销人"**。真实场景应该取当前登录用户。
4. **库没有迁移机制**。改表结构只能删库重来。D11 冻结前不会再改结构；
   如果真改了，我会写一段幂等的 `ALTER TABLE`，而不是让人删库。
5. **真模型仍未验证**。这条从 D2 挂到现在，只有一把真 key 能解。
6. **同批撞号会被判重复**。mock 只有 3 张固定样本，一次传两张不同图也可能撞到同一张样本，
   于是第二张判 `R1`。这是 mock 的局限，不是规则的错——但也说明 mock 不能当识别能力用。
